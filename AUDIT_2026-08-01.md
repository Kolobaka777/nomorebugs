# Аудит QA Learning Hub (baga-net) — 01.08.2026

Полный ревью силами «команды сеньоров» (security / backend / frontend / бизнес-логика / тесты / инфра). Только чтение кода, ничего не менялось. Общий вывод: база на удивление крепкая для внутреннего инструмента — параметризованные запросы, реальные транзакции в большинстве мест, тесты на 179 кейсов, рабочий CI. Ниже — конкретные пробелы, от самого срочного к косметике.

---

## 0. Срочно: регрессия из сегодняшнего фикса контейнера

**[CRITICAL]** `server/docker-entrypoint.sh:16` — `su` не прокидывает `SIGTERM` дочернему процессу Node. Аккуратный graceful-shutdown в `server/src/index.js` (закрывает соединения и БД за 10 сек) теперь никогда не вызывается — при каждом деплое Node убивается жёстко, а не штатно. Это side-effect именно сегодняшнего фикса read-only volume, не старая проблема.
**Фикс:** заменить `su` на `gosu` (устанавливается через apt, корректно прокидывает сигналы) — `exec gosu node "$@"` вместо `exec su -s /bin/sh node -c "exec $*"`.

Также по мелочи там же: `chown -R /data` гоняется рекурсивно на КАЖДОМ рестарте (растёт вместе с БД + 28 бэкапами) — стоит проверять владельца перед `chown -R`, а не гонять его вслепую каждый раз.

## 1. Безопасность

1. **[Medium]** Refresh-токен (живёт 30 дней) лежит в `localStorage` наравне с access-токеном (`client/src/auth.ts`) — короткий TTL access-токена специально задуман, чтобы XSS давал доступ только на 15 минут, но refresh в том же хранилище сводит эту защиту на нет. → вынести refresh-токен в httpOnly/Secure/SameSite-cookie.
2. **[Medium]** Саморегистрация полностью открыта (`app.js:352`, `POST /api/auth/register`) — любой, кто достучится до API, создаёт tester-аккаунт без инвайта/подтверждения почты/ограничения по домену.
3. **[Low/Medium]** Защита от брутфорса логина — только по IP (`app.js:270`, 20 попыток/15 мин), нет per-аккаунт счётчика — распределённая атака может брутфорсить один конкретный email без ограничений.
4. **[Low]** `react-router-dom` в диапазоне с известной High-CVE (GHSA-qwww-vcr4-c8h2, CSRF в RSC-режиме) — этот SPA RSC не использует, риск скорее теоретический, но фикс тривиален: `npm install react-router-dom@latest`.
5. **[Low]** Значения baseline/final survey (1-5) принимаются без проверки диапазона на сервере — можно записать произвольные числа, испортив дашборды «до/после».
6. **[Low]** `must_change_password` — это только фронтенд-напоминание, сервер не блокирует остальные запросы, пока флаг не сброшен — можно вечно игнорировать смену временного пароля.

**Хорошие новости:** SQL-инъекций нет, CORS — строгий allowlist, гайды/курсы рендерятся без `dangerouslySetInnerHTML`, IDOR по курсам/сабмишенам покрыт тестами, `npm audit` на сервере чист.

## 2. Бизнес-логика и целостность данных

1. **[CRITICAL]** Скрытый «внутренний рейтинг» (анти-чит) полностью доверяет данным от клиента (`app.js:955-1010`). `questionTimes`/`tabSwitches` шлёт браузер — прямой запрос к API с пустым `meta` или `tabSwitches: 0` автоматически проходит анти-чит-фильтр как «чисто». Ровно те же цифры видит лид как «мягкий флаг подозрительности» — то есть читер и не получит флаг, и получит скрытые баллы. → время на вопрос и переключения вкладки нужно считать на сервере, а не доверять клиенту.
2. **[CRITICAL]** Нет защиты от повторной прокачки наград. Пересдача уже пройденной лекции (`app.js:966-1010`) или тривиального чек-листа (`app.js:1682-1685`) каждый раз заново начисляет монеты и очки скрытого рейтинга без ограничения — можно фармить и магазин, и рейтинг бесконечно, просто пересдавая одно и то же. → начислять только за первый успешный результат по конкретной лекции/чек-листу.
3. **[Medium]** Архивированному (уволенному) тестировщику всё ещё можно начислить премию или выдать право доступа (`app.js:2928`, `2869`) — проверка роли есть, проверки `archived_at` нет. При восстановлении аккаунта такое право/премия тихо «оживает».
4. **[Low]** Время, проведённое в курсе (`seconds_spent`, `app.js:2527`), клиент репортит сам, без верхней границы и сверки с реальным временем — лид может увидеть накрученную метрику вовлечённости.

**Уже проверено и в порядке:** просроченные права реально перепроверяются на каждый запрос (не только при выдаче), доступ у архивированного пользователя обрубается сразу же (не ждёт истечения токена), хардделита пользователей нет нигде, гонки при параллельных запросах не актуальны — better-sqlite3 синхронный, один процесс.

## 3. Архитектура бэкенда

1. **[High]** `server/src/app.js` — 3228 строк, 90 роутов в одном файле. Уже есть чёткие секции-комментарии (auth, лид, админ, чек-листы, курсы, гайды, премии) — естественные границы для разбиения на отдельные роутер-файлы по доменам.
2. **[High]** Миграции схемы (`server/db/schema.js`, guarded `ALTER TABLE`) глотают ЛЮБУЮ ошибку пустым `catch {}` — не только «колонка уже есть». Сервер может подняться с поломанной схемой без единого сигнала об этом.
3. **[Medium]** `server/db/seed.js` разошёлся со реальной схемой — не хватает 15+ таблиц (чек-листы v2, кастомные курсы, гайды, права и т.д.). `npm run seed` сам по себе больше не создаёт рабочую dev-базу.
4. **[Medium]** Несколько многошаговых записей идут без транзакции там, где по логике файла должны — например, выдача/отзыв прав (`app.js:2882`, DELETE+INSERT без обёртки), архивирование/сброс пароля/смена роли (state+revoke-токенов+лог активности отдельными запросами).
5. **[Medium]** Разный формат ответов у похожих списочных эндпоинтов — где-то `{rows, hasMore}`, где-то жёсткий `LIMIT 50` без сигнала об обрезке, где-то просто «сырой» массив без пагинации вообще.
6. **[Low]** Ошибки бэкапов и здоровья БД логируются через `console.error`, а не через хелпер `logError()` — то есть именно самые важные инциденты не долетают до Sentry.
7. **[Low]** Если `ADMIN_EMAIL`/`ADMIN_PASSWORD` не заданы в проде — только предупреждение в лог, сервер всё равно поднимается «здоровым», но входить некому.
8. **[Low]** Мелкое дублирование — паттерн «загрузить user по id, 404 если нет» и апдейт bug_coins/premium_points скопипащены ~5 раз каждый.

## 4. Архитектура фронтенда

1. **[High]** `ChecklistsPage.tsx` — 1197 строк, 6 компонентов в одном файле (модалки импорта/экспорта/деталей + список + сама страница) вперемешку с логикой фильтрации, CSV/XLSX экспорта и статистики.
2. **[High]** `TeamMember.taskCounts` в типах помечен как обязательное поле, хотя сервер может его не прислать — сегодняшний краш команды именно из этого класса багов. Поправили в одном месте (`UleyPage.tsx`), но тип по-прежнему не заставляет защищаться остальные потребители. → пометить поле как опциональное в `types.ts`, чтобы TypeScript сам заставлял проверять.
3. **[Medium]** Данные о правах доступа и о команде запрашиваются заново на каждой странице, которая в них нуждается (3+ независимых вызова каждое) — нет общего кэша/дедупликации запросов.
4. **[Medium]** Паттерн «загрузка / ошибка+повтор / пусто / данные» руками копипастится в 19 файлах страниц (96 вхождений) — нет общего компонента-обёртки.
5. **[Medium]** Много `any` в типах API (`api.ts`, `types.ts`, `App.tsx`) — та же проблема, что и с `taskCounts`: типы не реально защищают от рассинхрона с сервером.
6. **[Low]** `CourseBuilderPage.tsx` (763 строки) и `ChecklistFormPage.tsx` (758 строк) смешивают загрузку данных, drag&drop-логику и глубоко вложенный JSX.
7. Размер бандла уже неплохо оптимизирован (exceljs и все страницы лениво грузятся) — если хочется ужать ещё, можно вынести Sentry/PostHog за динамический импорт.
8. Доступность в порядке — не нашли ни одной «глухой» кликабельной области без клавиатурной поддержки, цветовые индикаторы везде дублируются текстом.

## 5. Тесты и надёжность

1. **[High]** Клиент почти не покрыт тестами — 5 файлов, только unit-уровень (утилиты, один компонент). Ни один из ~20 экранов не протестирован целиком — вся проверка форм, курс-билдера, чек-листов держится на ручной проверке.
2. **[Medium]** Ошибки бэкапов не долетают до Sentry (см. пункт 3.6 выше).
3. **[Medium]** Health-check (`/api/health`) проверяет только чтение из БД (`SELECT 1`), не запись — как раз тот сценарий, что уронил прод сегодня утром (readonly-директория), health-check бы его не поймал.
4. **[Medium]** 8 из 9 рейт-лимитеров вообще не протестированы на срабатывание — только `loginLimiter` реально проверен тестом.
5. **[Low]** У `/api/lead/activity` нет своего теста.

**Хорошие новости, вопреки ожиданиям:** CI реально есть (`.github/workflows/ci.yml`, гоняет тесты сервера+клиента и typecheck на каждый пуш), идемпотентность миграций протестирована явно, Sentry/PostHog корректно самоотключаются без ключей.

## Что делать дальше (моя приоритизация)

1. Фикс `su` → `gosu` в entrypoint — регрессия сегодняшнего дня, ломает каждый деплой.
2. Анти-чит на сервере вместо доверия клиенту + защита от повторного фарма наград — реальная дыра в экономике баллов.
3. Проверка `archived_at` перед начислением премии/выдачей прав.
4. `ADMIN_EMAIL`/`ADMIN_PASSWORD` в DEPLOYMENT.md + чёткий restore-runbook для бэкапов — обе вещи почти ничего не стоят, а закрывают реальный риск «не смогу зайти» / «не смогу восстановиться».
5. Остальное — по мере сил, ничего не горит так же срочно.

Ничего из этого не внедряла — только нашла и описала, как договаривались.
