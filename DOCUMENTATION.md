# QA Learning Hub (baga-net) — техническая документация

Внутренний инструмент отдела тестирования: онбординг новых людей, курсы,
база знаний и лёгкая геймификация. Один сервер, один клиент, одна база.

Этот файл описывает, **как всё устроено и почему именно так**. Инструкции
по развёртыванию — в [DEPLOYMENT.md](DEPLOYMENT.md). Текущее состояние
готовности и список незакрытого — в [AUDIT_2026-08-19.md](AUDIT_2026-08-19.md).

---

## 1. Что это такое

Новый тестировщик приходит в команду и должен за несколько недель понять,
как тут заводят баги, какие бывают задачи и к кому идти с вопросом. Раньше
это жило в чужих папках с документами и в головах. Теперь — здесь.

Продукт держится на четырёх вещах:

| | Что даёт |
|---|---|
| **Жукадемия** | Фиксированный курс из 10 лекций с тестами. Порядок жёсткий: следующая открывается после сданной предыдущей. |
| **Курсы** | То же, но собирают лиды и сама команда: модули, уроки, тесты, пререквизиты, дедлайны. Тестировщик может предложить свой — уйдёт лиду на проверку. |
| **Багодельня** | Примеры багов «как плохо / как хорошо», словарь терминов, магазин косметики. |
| **Улей** | Взгляд лида: прогресс каждого, аналитика по лекциям, журнал действий, премии, права. |

Плюс гайды, доска идей, лента новостей команды и лягух-помощник в углу.

## 2. Как запустить

```bash
npm install                    # корень — только concurrently
cd server && npm install
cd ../client && npm install

cp server/.env.example server/.env   # заполнить JWT_SECRET
cp client/.env.example client/.env   # обычно можно оставить как есть

cd .. && npm run dev           # сервер :5001 + клиент :5173
```

На пустой базе в не-production окружении заводятся пять демо-аккаунтов
(`lead@qa.com` / `lead123`, `nazar@qa.com` / `test123` и ещё три
тестировщика) и демо-контент: десять шуточных тестов, гайды, примеры багов,
термины. Всё это **не создаётся в production** — см. §9.

```bash
npm test            # в server/ и в client/ по отдельности
npm run test:coverage
npm run backups     # server/ — список бэкапов
```

## 3. Архитектура

```
браузер ──► nginx (отдаёт статику клиента, ставит CSP)
              │
              └── /api ──► Node/Express ──► SQLite (один файл на диске)
```

Три решения, объясняющие почти всё остальное:

**SQLite, а не Postgres.** База — файл на постоянном томе. Команда 5–50
человек, запись редкая, чтение простое. Плата за это жёсткая и осознанная:
**приложение работает ровно в одну реплику**. Две реплики — это два процесса,
пишущих в один файл через сетевую ФС, то есть повреждённая база. Это записано
в DEPLOYMENT.md как эксплуатационное ограничение, а не как деталь.

**better-sqlite3, синхронный.** Ни одного `await` вокруг запросов, транзакции
— обычные функции. Работает потому, что запросы короткие и их немного; при
другом профиле нагрузки это было бы ошибкой.

**Никакого слоя кэширования.** Каждый запрос идёт в базу. При таком размере
данных это быстрее любого кэша и на порядок проще.

## 4. Роли и права

Три роли: **tester**, **lead**, **admin**. Роль лежит в JWT, но каждому
запросу перечитывается из базы — вместе с `archived_at` и
`must_change_password`. Понижение роли или архивация действуют немедленно,
а не после истечения токена.

Поверх ролей — **точечные права**, чтобы не приходилось делать человека
лидом ради одного раздела:

| Право | Что открывает |
|---|---|
| `manage_knowledge_base` | Багодельня: примеры багов, словарь, очередь заявок по ним |
| `manage_courses` | Создание и правка курсов, публикация, дедлайны |
| `manage_guides` | Гайды и их очередь заявок |

Права выдаёт лид, у них может быть срок. Админ приравнивается к лиду везде,
где проверка спрашивает «это лид?».

## 5. Аутентификация

```
POST /api/auth/login
  ├── access token  — JWT, 15 минут, в localStorage, в заголовке Authorization
  └── refresh token — случайная строка, 30 дней, httpOnly-cookie,
                      в базе только SHA-256 от неё
```

Access-токен короткий, потому что отозвать JWT нельзя. Refresh — длинный,
непрозрачный и **отзываемый**: смена пароля, смена почты и сброс пароля
гасят все сессии разом.

Флажок «Запомнить меня» на входе решает, сколько **браузер** хранит свою
копию refresh-куки, а не сколько живёт сессия. Снят — кука сессионная и
умирает вместе с браузером, так что на чужой машине вход не остаётся.
Серверная запись выдаётся и отзывается в обоих случаях одинаково, иначе
«выйти везде» пропускало бы такую сессию.

Клиент ловит 401 в перехватчике axios, идёт за обновлением **один раз** на
все параллельные запросы и повторяет их. Второго транспорта нет: `authFetch`
удалён, всё ходит через `api.ts`.

**Что защищает вход:**

- Лимитер по IP — 60 попыток / 15 мин, настраивается через `RATE_LIMIT_LOGIN`.
- Блокировка по аккаунту — 8 неудач подряд, 15 минут. IP можно менять, аккаунт нельзя.
- Одинаковая стоимость проверки для существующей и несуществующей почты:
  bcrypt считается всегда, иначе время ответа само по себе выдаёт,
  зарегистрирован ли адрес.
- Ответ на неверный пароль и на несуществующий адрес — байт в байт один.
- Неудачные попытки и срабатывание блокировки попадают в журнал лида.

Ещё есть вход через Telegram и восстановление пароля по почте — оба
необязательны и молча отключаются, если не заданы соответствующие переменные.

## 6. Данные

45 таблиц. Группами:

**Деньги.** `coin_ledger` — по строке на каждое начисление, с уникальным
ключом `(user_id, reason, ref_id)`. Он же и запрет двойной оплаты, он же и
ответ на «за что у этого человека столько монет».

**Люди.** `users` (учётка, роль, архив), `user_profiles` (ник, аватар,
косметика, баг-коины, премиальные баллы), `user_cards`, `user_badges`,
`granted_permissions`, `refresh_tokens`, `password_reset_tokens`,
`telegram_login_tokens`, `leave_periods`.

**Жукадемия.** `lectures`, `questions`, `test_results`, `baseline_survey`,
`final_survey`.

**Курсы.** `custom_courses` → `custom_modules` → `custom_lessons` →
`custom_quiz_questions`. Прогресс и результаты: `custom_lesson_progress`,
`custom_quiz_results`, `course_time_tracking`, `course_deadline_overrides`,
`custom_course_views`, `custom_lesson_notes`, `user_favorite_courses`,
`course_sections`.

**Знание.** `guides`, `bug_examples`, `glossary_terms`, `suggestions`,
`suggestion_likes`, `suggestion_folders`, `frog_lines`.

**Прочее.** `activity_log`, `team_events`, `bonus_awards`,
`internal_score_events`, `custom_avatars`, `schema_migrations`,
`seed_markers`, `_health_check`.

### Два правила, которые стоит знать

**Имя выводится, а не хранится.** У человека есть `users.name` (с чем
зарегистрировался) и `user_profiles.nickname` (как его зовут на самом деле).
Ни один запрос не выбирает `name` напрямую — все идут через
`displayName()` из `routeHelpers.js`, который берёт ник, а имя оставляет
запасным вариантом. Поэтому переименование действует задним числом на
трёхлетние записи и не требует миграции.

**Ключ к тесту не покидает сервер.** `correct_idx` и пояснение вырезаются
из ответа для всех, кроме тех, кто может редактировать курс. Проверка ответов
целиком серверная, ответы отправляются **по id вопроса**, а не по позиции —
курс, отредактированный между открытием и отправкой, не оценит человека по
другому вопросу.

### Миграции

Схема применяется заново при каждом старте: `CREATE TABLE IF NOT EXISTS`,
`PRAGMA table_info` перед `ALTER TABLE`. Каждый шаг обёрнут в
`migrationStep(name, fn)` и записывается в `schema_migrations` — так на
любую базу можно посмотреть и сказать, в каком она состоянии и какой шаг
упал, если упал.

## 7. Подсистемы

### Курсы

Курс — дерево: модули → уроки → вопросы. Урок бывает текстовым или тестом.
У урока есть пререквизит трёх видов: нет / рекомендация (не блокирует) /
обязательный (блокирует до прохождения).

Порог сдачи — **60%**, пересдач сколько угодно, засчитывается лучший
результат. Тест считается пройденным только **сданным**: попытки
недостаточно, и провал не двигает курс вперёд. Монеты за курс платятся,
только если он сдан, и только один раз.

**Гейт по модулям.** Модуль открывается, когда сданы все оценивемые тесты
всех модулей до него. Это серверное правило: в закрытом модуле нельзя ни
отметить урок пройденным, ни отправить тест. Автор курса не гейтится —
лид, идущий по своему черновику, его проверяет, а не проходит. Курс, в
котором нет ни одного теста, не запирается: правило про тесты не должно
закрывать курс, у которого их нет. Клиент зеркалит это правило локально,
чтобы сданный тест открывал следующий модуль без перезагрузки, но решает
всегда сервер — `/complete` и `/submit-quiz` проверяют заново.

Тестировщик может предложить свой курс — он уходит в очередь со статусом
`pending`. Лид одобряет, курс публикуется **под именем автора**, автору
капают монеты и приходит уведомление.

**Видимость.** Черновик виден только автору (и лиду, если это заявка на
рассмотрении). Это проверяется не только при открытии курса, но и на всех
маршрутах, адресуемых по id урока: оценка теста, показ пояснения, отметка
о прохождении, учёт времени, заметка. Отвечают они **404, а не 403** —
существование чужого черновика не дело спрашивающего.

### Экономика

Две валюты, намеренно несмешиваемые:

- **Баг-коины** начисляет сервис сам. Схема построена вокруг одного
  числа — **10 за пройденный модуль**, — и всё остальное кратно ему:
  +5 за тест модуля с первого раза, +15 за три модуля подряд с первого
  раза, +20 за итоговый тест, +30 за курс целиком, +25 за курс без единой
  пересдачи. Лекция старого трека — это один тест, поэтому платится как
  модуль: 10 за сдачу, +5 за первый раз. Одобренный материал — 100/60/30/20.
  Тратятся исключительно на косметику. Суммы — в `COIN_REWARDS`
  (`routeHelpers.js`), и это единственное их определение; лид видит ту же
  таблицу на вкладке «Рейтинг», читая её через `GET /api/coins/rules`.

  Каждое начисление проходит через `awardOnce()` и оседает строкой в
  `coin_ledger` с уникальным ключом `(кому, за что, за какой объект)`.
  Уникальный ключ **и есть** защита от двойной оплаты: вставка либо
  проходит, либо нет, монеты идут следом. До него каждое место платежа
  несло собственную проверку «а не платили ли уже», и награда, способная
  сработать из двух мест, не имела способа заплатить один раз.
- **Премиальные баллы** начисляет лид руками, с обязательной причиной.
  Потратить нельзя — это признание, а не деньги.

### Журнал

`activity_log` пишется **только** через `logActivity()`. Функция глотает
свои ошибки: потеря строки лога — меньшая беда, чем упавший из-за
бухгалтерии запрос пользователя (ровно этот класс бага один раз уже ронял
завершение курса в 500). Ошибка при этом уходит в Sentry.

**Попытки тестов видит только лид.** Каждая попытка пишется с вердиктом,
процентом и временем (`quiz_passed:100%:92s:Название`). Эти строки явно
исключены из `/api/me/activity`: отдать их обратно тому, кто их наделал,
значит превратить сводку по команде в перечень собственных провалов.

Записи делятся на четыре категории (`activityCategories.js`), и категорию
считает **SQL**, а не клиент — вторая копия правил в TypeScript оставалась
бы верной до первого действия, добавленного в одном месте из двух. Лид
фильтрует журнал по категории, человеку, тексту и диапазону дат — всё
складывается в один запрос.

### Лягух

Маскот в углу: сам подпрыгивает, изредка говорит подсказку, по клику
открывает чат-дерево. Весь текст — подсказки, фразы загрузки, шаги
первого входа — лежит в `frog_lines` и правится лидом в Багодельне.

Всё, что можно нажать, сформулировано **вопросом**. Кнопка в повелительном
наклонении заставляет командовать лягухом вместо того, чтобы спрашивать;
тест на это есть.

## 9. Первый запуск и production

На пустой базе поведение зависит от `NODE_ENV`:

- **не production** — заводятся пять демо-аккаунтов с паролями из этого
  репозитория плюс демо-контент.
- **production** — создаётся один админ из `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
  Без них сервер стартует, но громко предупреждает, что войти некому.
- **не production, но похоже на боевое** (задан `CORS_ORIGIN` или переменная
  хостинга) — сервер **отказывается стартовать**. Незаданный `NODE_ENV` —
  это не решение, а недосмотр, и цена недосмотра здесь — пять учёток с
  опубликованными паролями в интернете.

Образ сервера объявляет `NODE_ENV=production` сам, а `docker-compose.yml`
требует `ADMIN_EMAIL`/`ADMIN_PASSWORD` так же, как требует `JWT_SECRET`.

**Бэкапы.** Каждые несколько часов — копия базы на том, 28 ротаций. Если
заданы `BACKUP_S3_*`, каждая копия уезжает ещё и в S3-совместимое хранилище.
Пока они не заданы, сервер предупреждает при каждом старте: копии на том же
диске защищают от «уронили таблицу» и ни от чего больше.

Восстановление: `npm run backups` — список, `npm run restore -- --latest` —
накатить. Перед перезаписью делается копия того, что перезаписывается.

## 10. Тесты

**612 серверных** (68 файлов) и **313 клиентских** (41 файл).

| | Строки | Ветки | Функции |
|---|---|---|---|
| Сервер | 81% | 77% | 88% |
| Клиент | 59% | 54% | 45% |

Пороги стоят чуть ниже текущих значений и падают вместе с покрытием.
Порог, который падает в день установки, удаляют, поэтому он поставлен
там, где действительно держит.

Серверные тесты — настоящий HTTP через supertest поверх базы `:memory:`.
Один слушающий сокет на файл: несколько тысяч запросов через
listen/close на каждый давали случайные `ECONNRESET`.

Лимитеры живут в памяти процесса, а vitest делит воркер между файлами —
поэтому общий setup поднимает все `RATE_LIMIT_*` до недостижимых значений,
а два файла *про* лимиты задают свои. Без этого файлы делили бюджет
попыток, и набор падал через раз.

CI гоняет пять задач: серверные тесты с покрытием, клиентские с покрытием,
линт, сборку и `npm audit --omit=dev` по обеим половинам.

## 11. Соглашения

**Комментарии объясняют «почему», а не «что».** Строка, объясняющая, что
делает `map`, — шум. Строка, объясняющая, почему здесь именно `MAX(score,
excluded.score)`, — экономит следующему человеку полчаса.

**Один источник правды.** Суммы монет — в `COIN_REWARDS`. Цвета — в
`theme.ts` (хардкод `#e05252` встречался в 91 месте, пока не стал токеном).
Типографика — там же: `H1`–`H4`, `SMALL`, `BODY`, `LINK`. Заголовок

**Правило вместо перечня.** Там, где одна и та же ошибка повторялась
трижды, стоит тест на правило, а не на каждый случай: занятость нижнего
правого угла (`cornerLayout.test.ts`), заголовки на общей шкале
(`typeScale.test.ts`), парность ограждений кода в уроках, отсутствие
эмодзи в интерфейсе. Такой тест падает в день, когда правило нарушают, а
не в день, когда кто-то заметит это на скриншоте.

**Текст интерфейса — по-русски, на «ты», без канцелярита.** Ошибка говорит,
что произошло и что делать. Кнопка называет действие.

**Тест пишется на поведение, а не на реализацию.** Хороший тест переживает
рефакторинг и падает от настоящей регрессии.
