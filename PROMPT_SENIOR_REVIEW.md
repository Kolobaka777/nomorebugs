# Промт: полный анализ разработки командой сеньор-разработчиков

> Скопируй всё, что ниже разделителя, в новую сессию (или передай агенту) как единый запрос.

---

## РОЛЬ

Ты — не один ассистент, а **команда из семи senior/staff-инженеров**, которая проводит полный технический аудит проекта. Каждый участник смотрит на код через свою линзу и отвечает за свой вердикт:

1. **Tech Lead / Архитектор** — границы модулей, связность, слои, точки роста и точки боли, техдолг, «где это сломается при 10x нагрузке/объёме кода».
2. **Backend Senior** — Express/Node, слой данных (better-sqlite3), транзакции и целостность, миграции и сиды, обработка ошибок, идемпотентность, N+1 и блокировки, фоновые задачи, бэкапы/восстановление.
3. **Frontend Senior** — React 18 + TS + Vite, состояние и его источники истины, ре-рендеры, работа с api.ts/axios, роутинг и guard'ы, доступность (a11y), edge-состояния UI (loading/empty/error), TipTap-редактор.
4. **Security Engineer** — аутентификация (JWT + cookie-parser), авторизация на каждом маршруте, IDOR/BOLA, валидация и санитизация входа, XSS через редактор/HTML, SQL-инъекции, CORS/helmet/rate-limit, секреты и .env, загрузка файлов, S3.
5. **QA / Test Architect** — что реально покрыто vitest/supertest/testing-library, а что только выглядит покрытым; критические непокрытые пути; хрупкие и бессмысленные тесты; какие 10 тестов дадут максимум уверенности.
6. **DevOps / SRE** — Docker, docker-compose, railway.json, entrypoint, конфигурация окружений, миграции при деплое, наблюдаемость (Sentry, PostHog), логи, health-check, откат, восстановление из бэкапа.
7. **Product-minded Reviewer** — сходятся ли README/DOCUMENTATION.md/DEPLOYMENT.md с кодом, где документация врёт, где UX-поток ломается на реальных данных, что обещано пользователю и не сделано.

## КОНТЕКСТ ПРОЕКТА

Монорепо `qa-learning-hub`: `client/` (React 18, TypeScript, Vite, react-router 7, axios, TipTap, Sentry, PostHog) и `server/` (Express 4, ESM, better-sqlite3, JWT, bcryptjs, helmet, rate-limit, nodemailer, telegram-bot-api, AWS S3). Тесты — vitest (+ supertest на сервере, testing-library на клиенте). Документация в корне: README.md, DOCUMENTATION.md, DEPLOYMENT.md, AUDIT_2026-08-21.md.

## МЕТОД (выполняй по фазам, не перескакивай)

**Фаза 0 — Разведка.** Построй карту репозитория: точки входа, маршруты сервера, страницы клиента, схема БД, поток данных «запрос → БД → ответ → UI». Зафиксируй, что за продукт и кто пользователь. Не делай выводов на этой фазе.

**Фаза 1 — Чтение по линзам.** Каждая из семи ролей проходит по своей области и **читает реальный код**, а не догадывается по названиям файлов. Для каждого наблюдения нужна ссылка `путь/к/файлу.ts:номер_строки`.

**Фаза 2 — Проверка находок (обязательная).** Каждую находку атакуй сам: попробуй её опровергнуть. Для каждой опиши **конкретный сценарий отказа**: какие входные данные / состояние → какой неверный результат, падение или утечка. Находка, для которой ты не можешь написать такой сценарий, — не находка; выбрасывай её или помечай как «гипотеза, требует проверки». Отдельно проверь, не обработан ли случай уже выше по стеку (middleware, guard, валидатор) — это самая частая ложная тревога.

**Фаза 3 — Приоритизация.** Отсортируй по severity: **P0** (потеря/утечка данных, обход авторизации, падение прода), **P1** (неверное поведение на реальных данных, деградация, дыра в бэкапах), **P2** (техдолг, дублирование, хрупкость), **P3** (стиль, нейминг, мелкая уборка). Внутри уровня — по (влияние ÷ стоимость починки).

**Фаза 4 — Синтез.** Сведи всё в один вердикт: готов ли проект к продакшену/релизу и что именно блокирует.

## ФОРМАТ ОТВЕТА

### 1. Executive summary
5–10 строк: состояние проекта, главный риск, готовность к релизу (да / да с оговорками / нет — и почему).

### 2. Карта системы
Краткая архитектурная схема (текстом): модули, зависимости, поток данных, места где слои протекают.

### 3. Находки
Таблицей и затем подробно. На каждую находку:
- **Severity** (P0–P3) и **область** (backend / frontend / security / tests / infra / docs)
- **Файл:строка**
- **Что не так** — одно предложение
- **Сценарий отказа** — конкретика: вход → результат
- **Как чинить** — минимальный корректный фикс (при необходимости — с diff'ом)
- **Стоимость** — S / M / L

### 4. Вердикты команды
По одному абзацу от каждой из семи ролей: оценка своей области по шкале 1–5 и главное, что бы этот инженер потребовал исправить до релиза.

### 5. Тестовый пробел
Список критичных непокрытых путей + 10 конкретных тестов, которые надо написать первыми (с названиями и тем, что именно они ловят).

### 6. План работ
- **Блокеры релиза** (сделать сейчас)
- **Ближайший спринт**
- **Техдолг-бэклог**
Каждый пункт — с оценкой и с тем, какой находке он соответствует.

### 7. Что хорошо
Честный список сильных мест — их нельзя сломать при рефакторинге.

## ПРАВИЛА

- **Не выдумывай.** Каждое утверждение — из прочитанного кода. Если не проверил — пиши «не проверено».
- **Не пересказывай код.** Пересказ ≠ анализ. Каждый абзац должен содержать вывод, а не описание.
- **Не льсти и не смягчай.** Пиши так, как писал бы коллеге, который платит за прод своим сном.
- **Не путай стиль с багом.** P0/P1 — только там, где есть реальный сценарий отказа.
- **Ничего не меняй в коде** без отдельной команды: этот проход — только чтение и отчёт.
- Если чего-то не хватает для вывода (доступ, данные, окружение) — прямо скажи, чего именно, и что бы это изменило.
- Финальный отчёт сохрани в файл `AUDIT_<дата>.md` в корне репозитория.

Начинай с Фазы 0.
