Живой файл состояния между итерациями «полного аудита». Не история чата —

## Как читать этот файл

- **Done** — реально внедрено в код, лежит в рабочем дереве (не запушено —
  см. стандартное правило ниже).
- **Remaining** — известно, что нужно сделать, приоритизировано.
- **Decisions/assumptions** — решения, принятые без явного запроса
  (по инструкции «не останавливайся из-за неясностей»), с обоснованием.
- **Standing rule**: git-операции (commit/push/pull/etc.) выполняет только
  сама владелица проекта — я лишь готовлю патчи и даю точные команды.
  Аналогично (см. итерацию 1 ниже) — установку пакетов, тесты и сборку
  тоже запускает она сама через блок TERMINAL COMMANDS, не я.

### Done

1. **Refresh-токен перенесён из localStorage в httpOnly-cookie**
   (было `[Medium]` в AUDIT_2026-08-01.md, п.1 «Безопасность» — единственный
   пункт из старого аудита, который так и не был закрыт).
   - Сервер (`server/src/app.js`): новая cookie `refreshToken`, `httpOnly`,
     `Secure`+`SameSite=None` в проде (фронт и бэк — разные Railway-домены,
     это технически cross-site), `SameSite=Lax` в деве (localhost:5173 и
     localhost:5001 — один "site", разные порты), путь ограничен
     `/api/auth` — cookie физически не летит с обычными API-запросами.
     `POST /auth/login`, `/auth/register`, `GET /auth/telegram/poll/:token`
     теперь ставят cookie вместо поля `refreshToken` в JSON; `/auth/refresh`
     и `/auth/logout` читают её из cookie, а не из тела запроса.
   - Добавлена зависимость `cookie-parser` в `server/package.json` — **её
     нужно установить командой из блока ниже** перед запуском сервера.
   - Клиент (`client/src/auth.ts`, `api.ts`, `App.tsx`, `LoginPage.tsx`,
     `RegisterPage.tsx`, `TelegramLoginButton.tsx`): токен больше не
     хранится в localStorage вообще; axios и `fetch` теперь ходят с
     `withCredentials`/`credentials:'include'`, браузер сам прикладывает
     cookie где нужно. `clearSession()` на всякий случай подчищает старое
     значение `refreshToken` из localStorage у тех, кто был залогинен до
     этого изменения (иначе токен так и остался бы висеть в браузере,
     бесполезный, но всё ещё читаемый потенциальной XSS-инъекцией).
   - Тесты обновлены: `server/test/refresh.test.js` (переписан на
     `supertest.agent()` для куки), `registration.test.js`,
     `rate-limiters-auth.test.js`, `client/src/auth.test.ts`.
   - **Почему именно сейчас**: это был единственный некрытый Medium-риск
     из прошлого аудита, и XSS+localStorage-refresh — единственная
     комбинация, где короткий TTL access-токена (15 мин, специально
     сделан коротким) переставал что-либо защищать.
   - **Не смогла проверить сама** — по инструкции этой итерации не
     запускаю тесты/сборку/установку пакетов сама, только отдаю команды.
     Это первое, что стоит прогнать после `npm install` (см. ниже).

2. **`npm audit` (react-router-dom, High CVE, GHSA-qwww-vcr4-c8h2)** —
   **сознательно НЕ трогала**. `npm audit fix --force` предлагает
   *понизить* версию до 7.11.0 (ниже уязвимого диапазона 7.12.0–8.2.0) —
   это breaking change по словам самого npm, а уязвимость — про RSC-режим
   (React Server Components), которым это приложение (обычный SPA) не
   пользуется вообще. Понижать рабочую, стабильную зависимость ради
   теоретического риска — по-моему, того не стоит. Решение совпадает с
   выводом из прошлого аудита. См. вопрос в разделе ❓ ниже, если хочется
   пересмотреть.
