# baga-net — технический аудит

**21 августа 2026.** Полный проход семью линзами: архитектура, backend,
frontend, безопасность, тестирование, эксплуатация, продукт.

Метод: чтение реального кода со ссылками на строки, затем **обязательная
проверка каждой находки на опровержение**. Находка, для которой не
получилось описать конкретный сценарий отказа «вход → неверный результат»,
в отчёт не попала — таких было четыре, они перечислены отдельно в §8, чтобы
следующий проверяющий не тратил на них время заново.

Аудит проведён по рабочей копии, включающей правки от 21.08 (см. §7).
Кода не менялось: этот проход — только чтение, пробы и отчёт.

## 1. Резюме

Продукт — внутренний сервис онбординга QA-команды: лекции с тестами,
курсы от лида с модульным гейтом, багодельня, геймификация на баг-коинах.
Пользователей десятки, не тысячи; это определяет почти все инженерные
решения и оправдывает большинство из них.

**Состояние: зрелое.** Авторизация проверена системно — 35 привилегированных
маршрутов, ни один не пускает тестировщика, ни один не пускает запрос без
токена, ни один из 10 админских не пускает лида. Ответы тестов не покидают
сервер. Начисления идемпотентны через уникальный ключ. Миграции ведут
реестр и переживают повторный запуск. Развёртывание продумано до мелочей,
которые обычно узнают болью: проброс сигналов через `setpriv`, права на
том, CSP из origin API, health-чек с реальной записью.

**Главный риск — не в коде приложения, а в бэкапах.** Копии на том защищают
от «уронили таблицу» и ни от чего больше; офсайт в S3 существует, но
**восстановить из него нечем** — `scripts/restore-backup.js` не знает про S3
вовсе, а сама выгрузка читает базу в память целиком и тем хуже, чем база
больше. То есть единственная защита от потери тома не имеет ни инструмента
восстановления, ни теста на него, и деградирует ровно по мере роста данных.

**Готовность к релизу: да, с оговорками.** Блокеров в коде нет.
Блокирует один эксплуатационный пункт: настроить `BACKUP_S3_*` и **один раз
пройти восстановление**.

**Дополнено после починки (§6).** Все двенадцать находок закрыты, включая
путь восстановления из S3, которого не было вовсе, — `npm run restore:s3`
существует и покрыт round-trip тестом. Блокирующим остаётся то же самое и
по той же причине: тест против фейкового бакета не заменяет учения на
реальном томе.

## 2. Карта системы

```
                    браузер
                       │
        ┌──────────────┴───────────────┐
        │  client (nginx:alpine)        │  CSP собирается на старте
        │  React 18 + TS + Vite         │  из origin API
        │  21 страница, все React.lazy  │
        └──────────────┬───────────────┘
                       │  axios, Bearer + httpOnly-кука на /api/auth
        ┌──────────────┴───────────────┐
        │  server (node:20)             │  helmet · CORS-allowlist
        │  Express, 12 роутеров         │  rate-limit · compression
        │  ~137 обработчиков            │  request-id · JSON-логи
        └──────────────┬───────────────┘
                       │  better-sqlite3 (синхронный, WAL, FK on)
        ┌──────────────┴───────────────┐
        │  /data/learning_hub.db        │  47 таблиц, 69 индексов
        │  /data/backups/ ×28           │  + S3, если задан
        └───────────────────────────────┘
```

**Поток запроса.** `authMiddleware` (`src/auth.js:53`) проверяет схему
`Bearer`, подпись JWT, а затем **перечитывает роль и `archived_at` из базы** —
роль в токене не является источником истины, поэтому разжалованный лид
теряет права немедленно, а не через 15 минут. Дальше `requireRole` или
`requirePermission`, затем обработчик со своим `try/catch` (проверено: без
`try` остался один маршрут, `lead.js:405`, и там нечему падать).

**Слои держатся.** Роутеры не знают друг о друге; общее живёт в
`routeHelpers.js` с явным правилом «сюда только то, что нужно двум и более
доменам». Схема БД — один файл с идемпотентными шагами.

**Где слои протекают — три места:**

1. **Ручные зеркала клиент↔сервер.** `SHOP_ITEMS`/`SHOP_CATALOG` — по-прежнему
   парные копии, синхронизируются глазами. Разошедшуюся копию ценника монет
   21.08 удалили в пользу запроса к серверу, права на косметику — тоже; магазин
   остался последним. Класс дефекта доказан на практике, см. §7.
2. **Клиент дублирует серверные правила ради отзывчивости.** Гейт модулей
   считается и на сервере (`courses.js:172`), и в браузере
   (`CustomCourseLearningPage.tsx`). Это сознательно, но два места — это два
   места.
3. **`app.js` — 394 строки, из них половина не про маршрутизацию:**
   сид-пользователи, сид-контента, чистка токенов, лимитеры, health с
   расчётом порога по диску. Оно работает и хорошо описано, но растёт.

### P1-1 · Из офсайт-копий нечем восстановиться

`server/scripts/restore-backup.js` — **ноль упоминаний S3** (проверено
`grep -c`). `server/test/backup-offsite.test.js` проверяет только выгрузку.
`npm run restore` умеет читать исключительно локальный `BACKUP_DIR`.

**Сценарий отказа.** Том потерян — диск, ошибочный `railway volume delete`,
сбой провайдера. Вместе с ним исчезли и база, и все 28 локальных ротаций.
Единственные уцелевшие копии лежат в S3. `npm run restore --list` показывает
пустой список: каталога больше нет. Оператор в разгар инцидента вручную
ищет ключ в бакете, качает, кладёт в нужный путь, разбирается с
`-wal`/`-shm` — по пути, который никто никогда не проходил и который ничем
не покрыт.

То есть протестирована та половина, которая защищает от логической порчи, а
та, ради которой офсайт вообще заводят, не протестирована и не
инструментована.

**Как чинить.** Флаг `--from-s3` в тот же скрипт: список объектов по
префиксу, скачивание во временный файл, существующая проверка
`integrity_check`, дальше общий путь. Плюс тест round-trip против
поднятого фейкового S3 — `backup-offsite.test.js` уже умеет мокать клиент.
**Стоимость: M.**

### P1-2 · Выгрузка читает всю базу в память

```js
// server/src/backup.js:54
const body = fs.readFileSync(filePath);
```

Файл целиком попадает в `Buffer` перед отправкой. Аватары хранятся в базе
как base64 (`user_profiles.custom_avatar` до 2.8 МБ на человека плюс галерея
`custom_avatars`) — это осознанный компромисс, записанный в коде, и он же
делает рост базы линейным по числу пользователей с картинками.

**Сценарий отказа.** 100 человек загрузили аватары → база ~300 МБ. Каждые
6 часов процесс аллоцирует Buffer на 300 МБ поверх обычного потребления.
На контейнере с типичным лимитом это OOM-kill: контейнер перезапускается,
выгрузка не завершается, следующая попытка — через 6 часов, с тем же
исходом. Офсайт-копии тихо перестают появляться, и узнают об этом в тот
момент, когда они понадобились.

**Оговорка.** Механизм — факт из кода: `readFileSync` держит весь файл.
Сам OOM зависит от лимита памяти контейнера, который я **не измерял**.
Даже без OOM это пиковая аллокация размером с базу каждые 6 часов.

**Как чинить.** `fs.createReadStream` + `Upload` из `@aws-sdk/lib-storage`
(пакет уже в дереве зависимостей AWS SDK) — многочастная загрузка потоком,
константная память. **Стоимость: S.**

### P2-3 · GET-запросы не лимитируются вообще

```js
// server/src/app.js:288
skip: (req) => req.method === 'GET' || req.path.startsWith('/api/auth/'),
```

**Измерено:** 350 запросов подряд на `/api/stats` — **ноль ответов 429**.

**Сценарий отказа.** `/api/avatars/gallery/:id/image` отдаёт картинки из
базы; `/api/custom-courses` выполняет запрос с четырьмя коррелированными
подзапросами на каждую строку каталога. Обе — GET, обе доступны любому
аутентифицированному человеку без ограничений. Скрипт с валидным токеном
насыщает один синхронный процесс `better-sqlite3` до отказа: он однопоточный,
и каждый такой запрос занимает event loop целиком на время чтения.

Комментарий над лимитером честно называет себя «грубым подстраховщиком для
мутирующих методов» — то есть исключение GET сделано осознанно. Но GET здесь
не дешёвый.

**Как чинить.** Второй лимитер на GET с щедрым порогом (условно 1000 / 15 мин),
`skip` для `/api/health`. **Стоимость: S.**

### P2-4 · `/api/health` пишет в базу без аутентификации

```js
// server/src/app.js:341
db.prepare('INSERT OR REPLACE INTO _health_check (id, checked_at) VALUES (1, CURRENT_TIMESTAMP)').run();
```

Проба записи здесь **правильная по замыслу**: чтение проходит и на
read-only томе, поэтому проверять надо запись. Проблема в том, что ручка
не требует токена и не лимитируется (см. P2-3).

**Измерено:** 400 неаутентифицированных GET — **0 ответов 429**, WAL вырос
на 779 КБ (~2 КБ на запрос), пропускная способность в процессе ~1370 req/s.

**Сценарий отказа.** Постоянный поток на `/api/health` заставляет процесс
выполнять запись на каждый запрос. SQLite — один писатель на базу, поэтому
реальные записи (отправка теста, сохранение профиля, начисление монет)
встают в очередь за потоком чужого мусора.

**Оговорка.** Отсутствие лимита и запись на запрос — измерены. Само
вытеснение реальных записей — вывод из однописательской модели SQLite,
под нагрузкой я его **не воспроизводил**. Рост WAL ограничен
автоконтрольной точкой: диск так не переполнить, вопреки первому
впечатлению.

**Как чинить.** Кэшировать пробу записи: выполнять не чаще раза в 10 секунд,
остальным отдавать последний результат. Health-чекеру платформы этого
достаточно — он опрашивает раз в 30 секунд. **Стоимость: S.**

### P2-8 · 0% покрытия на graceful shutdown

`server/src/index.js` — **покрытие 0%**, строки 6–35. Это обработчик
SIGTERM: останавливает бота, останавливает расписание бэкапов, закрывает
сервер, закрывает базу, форсирует выход через 10 секунд.

**Сценарий отказа.** Регрессия, переставляющая `db.close()` до колбэка
`server.close()`, закроет базу под запросами в полёте. Каждый деплой
Railway шлёт SIGTERM — то есть отказ будет происходить при **каждом**
выкате, на записях, попавших в это окно, и выглядеть как загадочная
потеря данных, а не как ошибка деплоя.

Ирония в том, что `docker-entrypoint.sh` целиком написан ради сохранности
этого пути: там подробно объяснено, почему `su` заменён на `setpriv` —
`su` глотал сигнал и обработчик не запускался вовсе. Путь, который так
дорого защищали на уровне контейнера, не защищён ни одним тестом.

**Как чинить.** Вынести `shutdown()` в отдельный модуль и проверить
порядок вызовов на моках. **Стоимость: S.**

## 5. Тестовый пробел

Критично не покрыто: graceful shutdown (0%), доставка писем (18%),
интерцептор обновления сессии (0%), главная форма профиля (0.44%),
администрирование лекций (44%), глобальный обработчик ошибок.

Десять тестов, которые я написал бы первыми:

1. **`shutdown() закрывает базу только после того, как сервер отпустил соединения`** — ловит перестановку `db.close()` в обработчике SIGTERM, то есть потерю записей на каждом деплое.
2. **`восстановление из офсайт-копии поднимает базу целиком`** — round-trip выгрузка→скачивание→`integrity_check`→открытие. Ловит P1-1: сегодня такого пути нет вовсе.
3. **`выгрузка базы не держит файл в памяти целиком`** — проверка, что в `PutObject` уходит поток, а не `Buffer`. Ловит P1-2 и его возврат.
4. **`редактор профиля доносит до сервера все поля, а не только изменённые`** — ловит возврат дефекта, стиравшего профиль (§7, п.1), со стороны клиента; сервер уже прикрыт.
5. **`переключение вкладок в редакторе профиля не теряет введённое`** — 828 строк формы, где это единственный способ потерять текст молча.
6. **`просроченный access-токен обновляется один раз на все параллельные запросы`** — `auth.ts` схлопывает обновления; ловит регрессию, при которой пять одновременных 401 дают пять обновлений и гонку за последний токен.
7. **`неудачное обновление сессии разлогинивает чисто, а не оставляет полусостояние`** — второй половине интерцептора нужен тест не меньше первой.
8. **`письмо сброса пароля уходит, а сбой отправки не выглядит успехом`** — 18% покрытия на единственном канале восстановления доступа.
9. **`/api/health отдаёт кэш и не пишет в базу чаще раза в N секунд`** — фиксирует фикс P2-4 и не даёт вернуть запись на каждый запрос.
10. **`поток GET-запросов упирается в лимит`** — фиксирует P2-3; сегодня 350 запросов подряд проходят без единого 429.

Про восьмой и десятый честно: я их **не писал**, это проход только на
чтение. Первые семь описывают поведение, которое я прочитал в коде;
восьмой требует мока SMTP, которого в дереве тестов пока нет.

### P1-13, P1-14 · Корзина не вычищается

`hardDeleteCourse` удаляет каскад вручную, потому что внешние ключи
объявлены без `ON DELETE`, а `foreign_keys=ON`. Комментарии рядом описывают
ровно этот класс — «забыли таблицу, транзакция откатилась, курс застрял в
корзине навсегда» — и он был исправлен для `course_deadline_overrides`,
`course_time_tracking` и `custom_lesson_notes`. Оставались ещё два.

**Сценарий отказа №13.** Тестировщик сдал тест курса — появилась строка в
`custom_quiz_results` с FK на `custom_lessons`. Админ удаляет курс и чистит
корзину: `DELETE FROM custom_lessons` падает на внешнем ключе, транзакция
откатывается целиком, курс остаётся в корзине. Навсегда, без ручной операции
над базой. То есть **любой курс, которым реально пользовались**.

**Сценарий отказа №14.** `custom_lessons.prerequisite_lesson_id` — FK на саму
же таблицу, а уроки удаляются помодульно. Урок второго модуля, привязанный к
тесту первого, держит строки первого модуля, и падает самый первый `DELETE`.
Это форма, которую строят `seedFrontendCourses`, `backfillSequentialPrerequisites`
и вводный курс — то есть **все засеянные лекции и всё, что собрано
конструктором с последовательными пререквизитами**.

Проверено сверкой всех входящих FK через `PRAGMA foreign_key_list`: больше
незакрытых нет. Три теста; оба падали до правки на `SqliteError: FOREIGN KEY
constraint failed`.

### P2-15 · `work_days` принимал 400 КБ

Фильтр проверял, что каждое значение — валидный день недели, но не сколько их.
`'1,'.repeat(200000)` — это 200 тысяч валидных записей, они склеивались обратно
и сохранялись: **400 001 символ в одну строку профиля, ответ 200.**
`GET /api/team/presence` читает `work_days` у каждого участника и
`computeIsWorkingNow` разбирает его — одна отравленная строка перечитывается
при каждой загрузке доски команды всеми. Набор дней недели по определению не
больше семи; теперь дедуплицируется.

### P2-16 · Галерея аватаров без потолка

Размер одной картинки ограничен 2.8 МБ, количество — ничем. Проверено: 60
публикаций подряд, ни одного отказа. При 300 записях за 15 минут это порядка
800 МБ на том в 433 МБ — тот же том, где живая база и все 28 ротаций бэкапа;
заполнение останавливает не загрузки, а вообще все записи в приложении.
Плюс произвольный текст принимался как картинка: отдающий маршрут и так
отвечает на него 415, то есть показать такое было нельзя — это был чистый вес
в базе и битая плитка в галерее. Потолок 12 своих картинок, проверка data-URI
на входе, удаление освобождает место.

### P2-17 · Рунбук восстановления описывал не то

`DEPLOYMENT.md` вёл оператора через ручной `sqlite3 .restore`, **не упоминая
`npm run backups` / `npm run restore`** — скрипты, которые существуют, покрыты
тестами и делают проверку целостности до перезаписи и копию заменяемой базы.
Восстановления из S3 в рунбуке не было вовсе — сценария, ради которого офсайт
и заводят. Переписан: два пути по ситуации (том цел / тома нет), ручной
оставлен последним с явной оговоркой, что он не делает ни одной проверки.
Заявление «никогда не проверялось end-to-end» заменено на точное: механику
покрывают тесты, учения на реальном томе не было.

**Найдено при проверке собственной правки:** `npm run backups:s3` без
настроенных ключей отвечал внутренней ошибкой AWS SDK («No value provided for
input HTTP label: Bucket») вместо внятного сообщения, которое даёт
`--from-s3`. Все документируемые команды прогнаны вживую.

- **Двойное одобрение** термина и примера бага: второй раз 400, монеты

- **IDOR в предложениях**: правка и удаление проверяют владельца и окно в

- **Очистка корзины** для гайдов, терминов, примеров и предложений: входящий

- **Длина текстовых полей**: предложения, примеры, термины, гайды отвечают

- **Пользователи не удаляются жёстко** (архивация), у лекций нет маршрута

- **Edge-состояния клиента**: ошибки загрузки отделены от «пусто» на всех

### Ложная тревога, которую я снял с себя

Сортировка ленты новостей смешивает хранимое время SQLite без зоны (которое
`new Date()` читает как локальное) и UTC из `toISOString()`. Выглядело
находкой. **Написал тест — он не различает до и после**, и разбор показал
почему: виртуальные события штампуются временем запроса, поэтому всегда
сверху при любом парсинге, а хранимые сдвигаются все одинаково и порядок
между собой сохраняют. Ненаблюдаемо. Тест удалён, парсинг всё равно приведён
к `parseDbDate` — но как гигиена инварианта, а не как исправленный баг, и в
комментарии написано именно это.

синтаксиса сохранена — на сайте, который учит HTML/CSS/JS, потерять цвет в
примерах кода было бы регрессией, а не разменом; lowlight с девятью
грамматиками весит малую долю от того, что грузилось. Тоггл-список стал
настоящим `<details>`: вне редактора клик не нужно перехватывать, браузер
сворачивает сам и бесплатно даёт работу с клавиатуры.

Проверено на собранном бандле: чанк страницы урока **не ссылается на
редактор вовсе**; Багодельня и Гайды ссылаются, но через `lazy()` — то есть
подгружают только при открытии формы. 20 тестов на рендерер, включая
незнакомые узлы и разметку (документ из более новой версии редактора теряет
здесь оформление, но не слова).

### Падение одного экрана больше не уносит навигацию

`ErrorBoundary` была одна, на корне: любая ошибка рендера заменяла всё
приложение — вместе с шапкой и меню — полноэкранным «что-то пошло не так».
Теперь она принимает свой запасной вид и метку области, а маршрутизируемая
страница обёрнута отдельно. Ключ по `pathname`: иначе пойманная ошибка
залипала бы на всех последующих экранах, потому что граница держит состояние,
пока что-нибудь не сменит её идентичность.

### Ещё один остаток удалённой фичи

В админке жила вкладка «Настройки» с панелью **«Типы задач для чек-листов»** и
подписью «этот список появляется в выпадающем меню при отправке чек-листа» —
меню, которого нет с 15.08. Админ курировал справочник, который не читает
никто. Удалены панель, вкладка, три метода API, три маршрута и таблица
`task_types` — тем же осторожным способом, что и чек-листы: **только если
пуста**. 42 таблицы вместо 47.

### Аномалия покрытия — причина найдена

В §11 было записано, что `shutdown.js` отсутствует в отчёте о покрытии и
причина неизвестна. Найдена экспериментом: **убрать его тест — файл
появляется с 0%, вернуть — исчезает совсем.** Провайдер v8 теряет модуль,
который загружается только тестом, а не через граф приложения; `all: true`
не помогает. Это единственный такой модуль (всё остальное в `src/`
достижимо из `app.js`, который импортирует каждый второй тест). Записано в
самом модуле, чтобы следующий не начинал заново.

### Найдено по дороге

- **`bootstrap.js` при выносе** обнажил порядок, который был неявным и
  является несущим: страховочная копия обязана предшествовать `initDb()`, а
  посев пользователей — посеву контента, потому что контент атрибутируется
  реальному аккаунту лида. Теперь это написано там, где видно.
- **`AdminPage.test.tsx` мокал три метода API**, которых не стало вместе с
  панелью — тест продолжал бы «проходить», описывая несуществующий интерфейс.

## 9. Проверенные ложные тревоги

Записаны, чтобы следующий проверяющий не тратил на них время. Каждая
выглядела находкой и не пережила попытки её воспроизвести.

- **XSS через редактор.** Гипотеза: документ с незнакомым узлом уронит
  ProseMirror, а `<img src="javascript:...">` выполнится. Проверено пятью
  пробами рендера: незнакомые узлы, документ без содержимого, незнакомая
  разметка, пустой текстовый узел — всё отрисовалось без исключения.
  `javascript:` в `src` картинки браузером не исполняется, а CSP
  `img-src 'self' data: blob:` закрывает и внешние пиксели.
  `dangerouslySetInnerHTML` в проекте не встречается ни разу.
- **Пустой `IN ()` в командном запросе.** `lead.js:68` строит список
  плейсхолдеров динамически — но подстрахован через `|| 'NULL'`.
- **Мёртвое право `manage_checklists` в интерфейсе.** Список прав на
  клиенте (`uley/constants.ts:15`) и `KNOWN_PERMISSIONS` на сервере
  совпадают: три права, чек-листов ни там, ни там.
- **Утечка текста ошибки в 500.** Все маршруты, кроме одного безопасного,
  обёрнуты в `try/catch` — до глобального обработчика 500 не доходит.
  Осталась только версия на 400 (см. P3-11).

## 10. Что хорошо и что нельзя сломать при рефакторинге

- **Роль перечитывается из базы на каждом запросе** (`auth.js:93`). Не
  оптимизировать это обратно в чтение из JWT: тогда разжалование
  перестанет действовать до истечения токена.
- **Уникальный ключ `coin_ledger` как защита от двойной оплаты.** Не
  заменять на проверку «уже платили?» перед вставкой — она проигрывает гонку.
- **`displayName()` вместо хранения имени.** Переименование действует на
  все записи задним числом без миграции.
- **Ответы тестов выдаются по одному после ответа**, а не приходят
  списком. Не «оптимизировать» в один запрос.
- **Проба записи в health-чеке.** Кэшировать частоту можно, заменять на
  `SELECT 1` — нельзя: read-only том проходит чтение.
- **`setpriv` в entrypoint.** Не возвращать `su` — сигнал теряется и
  graceful shutdown не запускается.
- **Тесты на правило, а не на случай** — занятость угла, шкала заголовков,
  парность ограждений кода, отсутствие эмодзи, кнопки без копии
  `.btn-primary`. Один такой тест ловит целый класс регрессий.
- **Комментарии, объясняющие почему, а не что.** В этом коде почти каждое
  неочевидное решение несёт рядом историю отказа, из которой оно выросло.
  Это самая ценная вещь в репозитории после самих тестов.

## 11. Чего в аудите нет намеренно

**Ни одна страница не открыта в браузере.** Всё сказанное о вёрстке и UX
выведено из кода и тестов. У jsdom нет движка раскладки: тесты удерживают
классы и структуру, но не подтверждают, что ряд карточек визуально ровный.
Это самая большая слепая зона отчёта, и закрывается она проходом человека
по экранам, а не ещё одним тестом.

**Нагрузочного тестирования не было.** Числа в P2-3 и P2-4 получены
внутрипроцессными пробами через supertest, а не обстрелом развёрнутого
сервиса. Вытеснение реальных записей под нагрузкой — вывод из модели
SQLite, а не измерение.

**Лимит памяти контейнера не проверялся** — см. оговорку в P1-2. После
перевода выгрузки на поток вопрос снят по механизму (память больше не
зависит от размера базы), но замерен по-прежнему не был.

**`src/shutdown.js` отсутствует в отчёте о покрытии** — не 0%, а строки нет
вовсе, хотя семь его тестов проходят. **Причина найдена 22.08** (см. §6.6):
провайдер v8 теряет модуль, который загружается только тестом, а не через
граф приложения. Проверено экспериментом в обе стороны. Тесты реальны;
цифры по этому файлу просто нет.

**Один прогон серверного набора упал** на `checklist_templates` в момент,
когда схема правилась на лету. Три последующих прогона чистые, воспроизвести
не удалось. Считаю следствием правки во время прогона, но утверждать не могу.

**Восстановление из бэкапа не выполнялось** ни локально, ни на копии тома.
Существование `scripts/restore-backup.js` и `test/backup-restore.test.js`
проверено чтением; то, что процедура из DEPLOYMENT.md проходит на реальном
томе, — нет.
